# Стиль в подготовке, исполнении и QA

Новые `REFERENCE_PLAN` schema 8 содержат `style_rendering_contract` version 2, собранный
из уже выбранных и просмотренных STYLE источников. Имена, текущие хеши,
наблюдаемая манера и ограничения источника остаются в плане. Контракт не выбирает
стиль/референсы за автора, не открывает библиотеку и не добавляет изображения.
GENERATOR_DEFAULT не получает фиктивного STYLE. Исторические immutable планы
не переписываются и проверяются по своей прежней версии.
Schema 7 сохраняет прежний rendering contract version 1 и прежние правила QA;
новые проверки не изменяют уже исполненные immutable планы и их промпты.

STYLE определяет только способ изображения, отдельно от FACE/BODY/CLOTHES.
Не превращать выбранный identity кадр в новый rendering authority и не требовать
копировать манеру уже дрейфовавшего тела. Сохранять черты, телосложение, покрытие,
позу, крой, узор, палитру и все ограничения автора. Число fidelity — цель, а не
измеренный балл или сила провайдерного параметра.

Подготовщик автоматически добавляет короткий блок `[STYLE_RENDERING_AUTHORITY]`
до сценического текста. При подготовке через `generation_request` он указывает
номера STYLE из реального разрешённого manifest, а не из догадки. Risk assessment
выполняется уже над итоговым текстом. Manager и execution guard сверяют контракт,
точные STYLE роли, физические вложения и текущие bytes. После READY эти входы
остаются неизменными. Не редактировать блок вручную и не делать новый вызов ради
исправления регистрации существующего результата.
В version 2 блок также перечисляет реальные номера и роли остальных физических
вложений: identity/body/clothes задают своё содержание, но не манеру изображения.
Это помогает отличить фотографию телосложения от STYLE; JSON manifest сам по себе
генератору не виден. Роли берутся из разрешённого manifest, без новых референсов.

Манеру сначала описать по письменному профилю и минимальному подходящему
утверждённому набору. Источник лица не доказывает покрытие полного тела или
материалов: фиксировать ограничение в существующем source review. Число refs
не равно силе влияния. Не добавлять STYLE_SUPPORT, необязательные sources или
калибровку автоматически. Для CHARACTER_BASE остаётся один STYLE; обязательные
identity/clothing inputs сохраняются.

## Один визуальный проход

Сопоставить полноразмерный output с exact STYLE sources, сохраняя также
проверку личности/тела/одежды. Проверить:

| Ключ | Различающая проверка |
|---|---|
| `mark_scale` | Масштаб мазка/линии/фактуры относительно формы и фокуса, а не пиксельного разрешения; допустима неприменимость кисти к стилю без кистевых следов |
| `edges` | Распределение резких/мягких/потерянных краёв и линия по выбранному источнику; не одинаковый контур повсюду |
| `value_groups` | Структура света, полутона и тени; не только правильная экспозиция |
| `colour_structure` | Цветовые отношения и плоскости, а не одна совпавшая палитра; не копировать ненужный цветной контровой свет |
| `materials` | Кожа/ткань/металл/среда рисуются способом выбранного стиля с сохранением конструкции |
| `detail_hierarchy` | Распределение крупных масс и выбранной детализации; избегать равномерной мелкой мозаики для стиля, которому она не свойственна |

Эти оси не навязывают всем стилям широкую кисть: фотореализм, line art и иные
манеры сравниваются со своими источниками. В LORANDESORE оценивать связанные
цветовые массы, крупные прядевые группы, выборочную линию и края; увеличение
мазка само по себе не даёт PASS и не должно превращать лицо в грубые плиты.

В существующий `--visual-review-json` добавить `style_review`:

```json
{
  "style_review": {
    "status": "PASS",
    "sources": [{"path": "<точный STYLE path из исполненного плана>", "sha256": "<его SHA-256>"}],
    "criteria": {
      "mark_scale": {"status": "PASS", "evidence": "<сравнение конкретной области source и output>"},
      "edges": {"status": "PASS", "evidence": "<наблюдаемое распределение краёв>"},
      "value_groups": {"status": "PASS", "evidence": "<конкретные светотеневые группы>"},
      "colour_structure": {"status": "PASS", "evidence": "<наблюдаемые цветовые отношения>"},
      "materials": {"status": "PASS", "evidence": "<способ изображения видимых материалов>"},
      "detail_hierarchy": {"status": "PASS", "evidence": "<где крупные массы и где детали>"}
    },
    "regions": {
      "materials": {"status": "PASS", "evidence": "<материалы и одежда отдельно от дизайна>"},
      "background": {"status": "PASS", "evidence": "<фон соответствует выбранной манере>"}
    }
  }
}
```

В `regions` также обязательны `face` при видимом лице и `body` при полном росте,
поясном кадре (`HALF_BODY`, `canvas_contract.body_visible`) или body stage;
у каждой строки собственный статус и видимый факт сравнения. Кадр только лица
и сцена без персонажа не получают фиктивную проверку тела.
Для отсутствующего фона/материалов и действительно неприменимого `mark_scale`
допустим `NOT_APPLICABLE` с конкретным `reason`; видимое лицо/тело так исключать
нельзя. В schema 8 остальные пять критериев рендеринга обязательны: нехватка
наблюдений даёт `NOT_CHECKED`, а не исключение критерия. Поэтому совпадение
палитры с пятью исключёнными осями больше не позволяет получить PASS.
Все шесть ключей criteria сохраняются.

Не копировать PASS из примера: это схема, не готовое ревью. `FAIL` любого
сравнения даёт итоговый FAIL; `NOT_CHECKED` не позволяет принять изображение.
У новых планов аргумент `--qa-style PASS` не отменяет результат этого сравнения.
Никакой валидатор не может доказать истинность визуальной аттестации: root
отвечает за реальный осмотр, целое ТЗ и решение REVISE/REVIEW_REQUIRED/ACCEPT.
Проверка отчёта также сверяет весь `execution_call` плана с immutable snapshot
исполненной попытки: совпадение одного хеша промпта не заменяет совпадения
физических вложений и их ролей. При штатной регистрации эта связь проверяется
также до приёмки отчёта.

## Исправления

При style drift возвращаться к исходным разрешённым STYLE и identity/clothing
sources, исправлять доказанный конфликт. Не строить цепочку full-frame edits от
отвергнутых результатов. В direct one-step edit нет нового обязательного guard,
меню или receipt: сравнить стиль с выбранным approved STYLE, если он применим,
но не добавлять его физически без необходимости/допуска и не подменять target.
Текстовое «preserve» не обеспечивает pixel lock; настоящая неизменность вне
области требует локального метода и сравнения пикселей. Не обещать её для
обычного генеративного edit. Никаких тестовых/калибровочных изображений без
отдельного поручения.
